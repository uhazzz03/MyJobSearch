Feasibility study & architecture brief

MyJobSearch app
can it actually be built?

A job-hunt copilot that finds roles by keyword, tracks every application through the hiring funnel, and drafts a cover letter matched to each job description and your CV. This brief works out which parts are real, where Seek and LinkedIn get in the way, and how to scope it so it stands up as a portfolio project.

Project  MyJobSearch app Type  Portfolio / learning Date  2026-09-03 Status  Scoping

The verdict

Build it. Two of the three features — application tracking and AI cover-letter generation — have no meaningful blockers. The third, discovering roles by keyword, works cleanly through job-aggregator APIs but not through Seek or LinkedIn directly: neither offers a job-search API to individual developers, and automating around that sits against their terms of service.

The fix is a source-agnostic ingestion layer plus a user-initiated browser capture for the two sites that dominate the Australian market. Scoped that way it is a 3–6 weekend build that demonstrates retrieval-augmented generation, semantic matching, resume parsing, a real evaluation harness, and — a genuine interview talking point — a deliberate, defensible data-sourcing decision.

§01

What you asked for

Three user stories, in your words, restated as scope:

  • Discover. “When I enter keywords, find matching jobs from Seek and LinkedIn.”
  • Track. “Keep a record of every application I can update — when I applied, and how far I got in each company's hiring process.”
  • Tailor. “For a job I want, read its description, match it against my CV, and generate a cover letter that reflects the fit.”

The rest of this brief takes each one, rates how feasible it is, and then deals with the one hard constraint that cuts across all three: where the job data comes from.

§02

Feasibility at a glance

Feature 01

Keyword job discovery

Partial

Aggregator APIs (Adzuna, Jooble) give real keyword + location search with Australian coverage and free tiers. Per-company boards (Greenhouse, Lever, Workable) are public and structured. Seek and LinkedIn specifically have no consumer search API — those are covered by browser capture instead (§03).

Feature 02

Application tracker

Feasible

Plain CRUD over a status pipeline, per-role notes, reminders, a timeline, and a funnel dashboard (response rate, time-to-first-reply, stage conversion). Optional AI layer: read-only Gmail parsing that suggests status changes from recruiter email.

Feature 03

Cover-letter generation

Feasible

The centrepiece. Parse the CV, embed it, semantically match its evidence against the job description, then have an LLM produce a match score, a gap analysis, and a grounded draft. Guardrail: the model may only assert skills present in the CV and must flag unmet requirements rather than invent experience.

Feature 02 — the tracker, in detail

A status pipeline is the backbone. A realistic set of stages:

SavedAppliedPhone screenTake-home InterviewFinal roundOffer RejectedGhosted

Around that: a free-text note and next-action date per role, a per-role event log (“recruiter emailed 12 Aug”), and a dashboard that turns the log into numbers — applications per week, reply rate, median days to first response, conversion at each stage. None of this needs AI. The optional AI layer is a read-only Gmail connection (OAuth) that scans for recruiter mail and proposes a status change for you to confirm — legitimate because it is your own inbox and your own consent.

Feature 03 — the cover-letter pipeline

  • Upload CV → extract text (pdfplumber / python-docx) → pull skills and experience with spaCy NER → chunk and embed.
  • For a target role: embed the job description, then run semantic matching (sentence-transformers) between each JD requirement and the CV evidence.
  • Feed CV chunks + JD + match table to the LLM (Claude API) and produce three artefacts: a match score with gap analysis, a grounded cover-letter draft, and resume-tailoring suggestions plus an ATS keyword-coverage score.
  • Guardrails: every claim in the letter must trace to a CV chunk; unmet requirements are surfaced, not papered over; nothing is ever auto-sent.

§03

The data-acquisition problem

This is the crux of your question. “Get jobs from Seek and LinkedIn via a real API” is the one part of the vision that does not map onto something you can just sign up for. Here is the honest landscape.

SourceOfficial APIFit for keyword searchVerdict
Adzuna Yes — free tier, API key Keyword, location, salary; genuine AU coverage Use as default
Jooble Yes — free key Aggregator; decent AU coverage Secondary source
Greenhouse / Lever / Workable Yes — public, no auth Per-company boards; clean structured JSON First-class
The Muse / Arbeitnow / Remotive Yes — free More remote / global than AU-specific Optional
Google Jobs Only via SerpAPI (paid) or Cloud Talent Solution Talent Solution builds your own board, not a query API Paid / indirect
Seek Partner-gated; hiring side only No consumer job-search endpoint exists Capture instead
LinkedIn No job-search API for developers Scraping breaches the User Agreement & is enforced Capture instead

Seek, specifically

The SEEK Developer API is real but built for the hiring side — job posting, “Apply with SEEK”, and ad-performance data — aimed at recruiters and recruitment-software vendors. Access goes through an integration request form and a partner manager. There is no endpoint that returns job listings for a keyword search. Realistic paths for you: an approved partner integration (not attainable for a solo project), a paid third-party scraper (cost, plus it still rests on scraped data), or user-initiated capture (below).

LinkedIn, specifically

There is no LinkedIn API for searching or extracting job listings. The Job Posting API exists only for approved distribution partners pushing jobs in, and that partner programme is not accepting new applicants. Automated scraping violates the LinkedIn User Agreement, and LinkedIn enforces it — auth walls, IP blocking, and litigation (the data provider Proxycurl was shut down after LinkedIn legal action). The hiQ v. LinkedIn case is often cited as “scraping public data is legal,” but it actually ended with hiQ found to have breached LinkedIn's terms: the CFAA does not reach public data, but the contract you accept still binds you.

The workaround that actually holds up

A Manifest V3 browser extension. While you are browsing a job on Seek or LinkedIn in your own logged-in session, you click “Save to MyJobSearch.” A content script reads the visible job description, title, company, and URL and POSTs them to the app. One page at a time, user-initiated, no crawler, no stored credentials, no rate limit to trip. It works identically on Seek, LinkedIn, or any company careers page.

This is both the compliance story and a real feature. In an interview, “I chose not to scrape LinkedIn and built a user-consent capture flow instead” reads as engineering judgement, not a gap.

Net design consequence: build ingestion behind a connector interface (search(keywords, location) → Job[]). Ship Adzuna and a Greenhouse/Lever connector as automated sources; ship the extension as the Seek/LinkedIn path; leave a documented stub where a paid provider could slot in later.

§04

System architecture

The seam that matters is the connector interface: every source, API or capture, produces the same Job record, so the rest of the system never knows or cares where a listing came from. Everything downstream of storage is standard: an embedding-based matcher, an LLM call with retrieval, and a thin UI.

§08

Limitations, stated plainly

  • Seek has no consumer API. Your options are an approved partner integration (recruiter-oriented, not realistic solo), a paid third-party scraper (cost + it's still scraped data), or the browser capture.
  • LinkedIn has no job API for this use. Automated scraping breaches the User Agreement and is actively enforced. Use capture or manual paste; do not ship a scraper in a project you put your name on.
  • Aggregator free tiers have rate limits and only partial coverage of the AU market — which Seek dominates. The capture flow is what closes that gap in practice.
  • LLM output needs a human every time. Anti-fabrication guardrails reduce risk but don't remove it; treat the match score as advisory and never auto-send a letter.
  • Gmail parsing is noisy. Recruiter mail is inconsistent; surface suggestions for confirmation rather than mutating state directly.
§09

Putting it on your CV

  • Describe it as an “AI-assisted job-application copilot” — retrieval-augmented generation, semantic JD↔CV matching, NER-based resume parsing, and an evaluation harness with real numbers.
  • Lead the interview story with the data-sourcing decision: you assessed the Seek and LinkedIn APIs, found no compliant path for automated search, and built a user-consent capture flow instead. That's the judgement signal.
  • Have three numbers ready: precision@k on the match ranker, claim-support rate on generated letters, and p95 latency + cost per letter.
  • Keep the repo honest: a short “Limitations” section in the README, mirroring §08, reads as maturity, not weakness.
